**Phase 3 — Backend (`apps/api`):**
- NestJS bootstrap: global guard chain (`RateLimitGuard` → `JwtAuthGuard` → `AuthorizationGuard`, registered via `APP_GUARD`) + `GlobalExceptionFilter` (`APP_FILTER`), all in `CommonModule`. - `AuthModule`: register (OTP-gated activation) → verify-otp → login (lockout after 5 failed attempts, 15 min) → refresh (rotating opaque tokens, reuse-detection revokes the whole session family) → logout → forgot-password → reset-password (revokes all sessions) → sessions list/revoke → `me`. OTP: 6-digit, argon2-hashed, 5 min TTL, 5 max attempts, 30 s resend cooldown, 5/hour cap. No-enumeration on login and forgot-password (verified by test, not just by inspection).

- `AuditInterceptor`/`AuditService` scaffold — `AuditLog` rows written on register/login/logout/password-reset today; wired for every future mutating route.
- `packages/validation/src/auth.ts` — the Zod schemas for every `/auth` DTO, shared verbatim between the API's `ZodValidationPipe` and both clients' `react-hook-form` resolvers (one schema, never duplicated). Fixed a real bug in this pass: `verifyOtpSchema`/`resetPasswordSchema`'s `code` field used `.length(6).regex(...)` — a code with the wrong length fell through to Zod's generic `"String must contain exactly 6 character(s)"` instead of the intended `"Code must be 6 digits."`, since `.length()` fires before `.regex()` and had no custom message. Fixed by giving `.length()` the same message.

**Four pre-existing infrastructure gaps, discovered (not introduced) while doing the above, and fixed in this pass:**
1. `apps/api/src/main.ts` never loaded `.env` for local dev (`pnpm --filter api dev`) — no `dotenv` import anywhere, so a real developer following `CLAUDE.md`'s documented `pnpm --filter api dev` command would hit "Invalid environment configuration" immediately on a fresh checkout. Fixed with a guarded `import "dotenv/config"` at the top of `main.ts` (no-ops if `.env` doesn't exist; never touches the test suite, which never imports `main.ts`).
2. `packages/config/src/schemas.ts`'s optional URL env vars (`SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_DSN`, `EXPO_PUBLIC_SENTRY_DSN`, `OBJECT_STORAGE_ENDPOINT`, `RATE_LIMIT_REDIS_URL`, `API_INTERNAL_BASE_URL`) used `z.string().url().optional()` — but every `.env.example` sets these to `""` rather than omitting them, and `.optional()` doesn't help against an empty string. Copying `.env.example` to `.env` verbatim (the documented setup step) would hard-crash on startup. Fixed with a shared `optionalUrl` helper that treats `""` as unset before validating.
3. `apps/mobile/jest.config.js`'s `transformIgnorePatterns` — copied from Expo's standard template, which assumes a flat `node_modules/react-native/...` layout — never matched pnpm's nested `node_modules/.pnpm/<name>/node_modules/<name>/...` layout, so **no mobile test had ever successfully run** in this repo (`passWithNoTests: true` masked it since zero test files existed before this phase). Fixed with an optional `(\.pnpm/[^/]+/node_modules/)?` prefix; also added `maxWorkers: 1` (parallel jest-expo workers were exhausting available memory in this sandbox) and a `moduleNameMapper` for the `@/*` alias (needed once real imports existed to test against).
4. **`apps/api`'s `dev` script (`nest start --watch`, `tsc` builder) could not actually run at all.** It failed resolving `@hospital/database` (and any other workspace TS package): that package's `"main"` points at raw `./src/index.ts` — this monorepo consumes workspace packages as TS source everywhere (see `apps/admin`'s `transpilePackages` note), which only ever worked for `apps/api` in tests because `ts-jest` transpiles the whole dependency graph itself; plain `tsc`+`node` was never going to resolve a raw `.ts` "main". **Tried and reverted first:** `tsx watch src/main.ts` does fix the resolution problem (esbuild-based, confirmed working, NestJS DI included) but breaks `@nestjs/swagger`'s route-parameter introspection (`TypeError` in `ParameterMetadataAccessor.explore` — esbuild's decorator-metadata emission isn't a safe drop-in here). **Fixed properly** with `node -r ts-node/register/transpile-only --watch src/main.ts` — `ts-node` uses the real TypeScript compiler (not esbuild), so `emitDecoratorMetadata` stays correct while still transpiling workspace `.ts` on the fly. Verified end-to-end against the pglite stand-in: clean boot, `/health` and `/health/ready` (real DB check) both respond, `/api/v1/docs-json` (the thing that broke under `tsx`) responds correctly, a real `/auth/login` against seeded demo data succeeds and issues a working JWT, and `--watch` correctly detects a source-file edit and restarts the process (confirmed twice). `build`/`start` (`nest build` + `node dist/main.js`) share the identical root cause and remain unfixed — out of scope for this pass (which was scoped to the dev server specifically) but a real gap before Render deployment (Phase 15); the same `ts-node`-based approach, or building workspace packages to real JS with `"main"` pointing at `dist/`, are the two realistic fixes.

**Phase 4 — Backend (`apps/api`):** `HospitalsModule` (Super Admin only, `PLATFORM` scope, no tenant filter by definition), `BranchesModule`, `DepartmentsModule`, `UsersModule` (invite → activate → deactivate lifecycle) — four new domain modules, all wired into `AppModule`.
- **Tenant scoping**, unified across all three hospital-scoped modules via one helper, `apps/api/src/common/tenant-scope.util.ts`'s `resolveHospitalId(actor, suppliedHospitalId)`: an Admin's own JWT-embedded `hospitalId` always wins (a client-supplied value is silently ignored, never trusted — docs/18-MULTI-TENANCY.md point 3); a Super Admin (`hospitalId` is `null` on their own token) must name one explicitly (body field on writes, `?hospitalId=` query param on reads) or the request is rejected with `VALIDATION_ERROR` rather than silently defaulting to "every hospital." `DepartmentsService.create`/`update` additionally cross-check a supplied `branchId` actually belongs to the resolved hospital (docs/18 point 4, defense-in-depth against a cross-tenant object reference).
- **Staff invite → activate → deactivate**, resolving a genuine gap in docs/16-AUTHENTICATION.md's one-line "Staff activation" description into a concrete, tested protocol (and updating that doc section to match, since the original text under-specified it): `POST /users/invite` creates a `PENDING_ACTIVATION` `User` (+ linked `Staff` row for Nurse/Receptionist/Admin roles — a Doctor invite creates neither `Staff` nor `Doctor`, deferred to Phase 5's `POST /doctors`) and signs a 72h RS256 **activation token** (new `ActivationTokenService`, `apps/api/src/common/jwt/`, same keypair as access tokens, distinguished by a `typ: "activation"` claim so the two can never be confused). Completing it needs **two** more calls, mirroring `/auth/forgot-password` → `/auth/reset-password`'s existing shape: `POST /users/activate/request-otp` (new endpoint, added to docs/15-API-SPECIFICATION.md in this pass) sends a fresh OTP under a new `ACCOUNT_ACTIVATION` `OtpChallenge` purpose (new enum value — additive migration `20260902120000_add_account_activation_otp_purpose`, docs/13-DATABASE-DESIGN.md updated); `POST /users/activate` verifies that code (cross-checked against the token's own `sub` so one invitee's challenge can never activate a different account), sets the password, and flips the user to `ACTIVE`.
- **Hospital suspension blocks login**: `Hospital.status = SUSPENDED` now rejects `POST /auth/login` with a new `AUTH_HOSPITAL_SUSPENDED` (403) — checked only *after* password verification, so a suspended hospital's existence is never an enumeration signal (docs/16-AUTHENTICATION.md "Login flow" and docs/28-ERROR-HANDLING.md updated). This is docs/18-MULTI-TENANCY.md's "What 'suspended' means for a Hospital" made real; existing sessions are not force-revoked (blocks new logins only — reversible, non-destructive, matching what's actually documented rather than inventing extra invasiveness).
- New error code `AUTH_ACTIVATION_TOKEN_INVALID` (400) for a missing/malformed/expired/wrong-purpose activation token — added to docs/28-ERROR-HANDLING.md and `packages/shared/src/errors/error-codes.ts` first, per the standing "codes are added there before code uses them" rule.
- `AuditInterceptor` (built but unused in Phase 3) got its first real callers here: `@Audit(...)` on every Hospital/Branch/Department mutation; `UsersService` calls `AuditService.record()` directly for invite/activate/deactivate/role-assign (needs before/after context the generic interceptor can't infer).
- **A real, previously-latent bug found and fixed while building this**: combining `@CurrentUser()` with a method-level `@UsePipes(schema)` silently runs the *actor* object through that same Zod schema too — `@Req()`/`@Res()` are exempt (Nest's built-in param types), but a custom `createParamDecorator()` like `@CurrentUser()` is not. Every `list`/`create`/`invite` handler that combined the two (plus `revokeSession` in `AuthController`, dating back to Phase 3 and never caught because no test exercised it) was hard-failing every request with `VALIDATION_ERROR`. Fixed by switching to per-parameter pipes (`@Body(new ZodValidationPipe(...))`) everywhere this pattern occurs — caught immediately by this phase's own integration tests (every write returned 400 before the fix), which is exactly why those tests exist.
- Verified via 34/34 passing integration tests, new: `apps/api/test/tenant-management.integration-spec.ts` (Hospital/Branch/Department CRUD, cross-tenant 404s, Super-Admin-required-hospitalId, hospital-suspension-blocks-login) and `apps/api/test/users.integration-spec.ts` (full invite→request-otp→activate→login lifecycle, Doctor-invite-skips-Staff-row, duplicate-email 409, wrong-purpose-OTP rejection, deactivate-revokes-sessions-immediately, tenant isolation, non-manager 403) — plus the existing 16 auth + 17 unit tests, all still green. New fixture helpers in `apps/api/test/fixtures.ts` sign real access tokens via the same `AccessTokenService`/`AuthzResolverService` the login flow uses, rather than hand-rolling test-only JWTs.

## Known issues

- **Docker unavailable in this development environment** (carried over from Phase 2). All Phase 3/4 integration-test verification used `@electric-sql/pglite` + `pglite-socket` as a temporary WASM Postgres stand-in (never committed, recreated fresh per verification session), requiring two non-default Prisma connection-string flags (`?pgbouncer=true` to disable named prepared statements, `&connection_limit=1` to avoid the stand-in's concurrent-connection limitation) — both are artifacts of that specific tool, **not** requirements of the real docker-compose/Supabase Postgres this project targets. Confirm the full `pnpm quality` (including `test:integration`) against real Docker before trusting this as final proof.
  - **New this phase, sharper than previously documented:** with `connection_limit=1`, the stand-in tolerates exactly **one** live Prisma client at a time. Now that `test/` has three integration spec files instead of one, plain `pnpm test:integration` (Jest's default parallel workers) has each file open its own connection simultaneously and they starve each other (`Can't reach database server`) — `--runInBand` (serial) is required against this stand-in specifically. Worse, the stand-in occasionally wedges into a permanently-unreachable state after an *abrupt* process kill (e.g. a sandbox interruption mid-run) rather than cleanly freeing its one slot — recoverable only by killing and restarting the pglite process itself (a plain retry of the connecting client is not enough). Neither is a real constraint of Postgres/Supabase, which handles concurrent connections and ungraceful client death normally; noted in this much detail because it cost real time to re-diagnose mid-phase and a future session hitting "works standalone, fails when run alongside anything else" against this stand-in should reach for `--runInBand` and a hard pglite restart before suspecting application code.
- **No simulator, Expo Go, or device available in this sandbox for `apps/mobile`.** The 6 new screens are verified via component tests only (React Native Testing Library) — real-device concerns (SecureStore's actual OS-level Keychain/Keystore behavior, real keyboard/`inputMode` behavior, actual navigation transitions, real network timing) are unverified. `expo start --web` was not attempted this pass; it's a plausible partial substitute (react-native-web) worth trying in a future session if a simulator remains unavailable.
- `packages/ui/web` and `packages/ui/native` were empty Phase 1 placeholders (`export {}`) until this phase — both now have their first real components (5 in each), sized exactly to what the auth screens needed. Expect them to grow again alongside Phase 4's admin shell (`T-405`) and Phase 5's patient-facing screens.
- Same carryover from Phase 1/2: the `jest-expo`/`expo-router` React 19 RC peer-dependency warning (harmless, `pnpm install` still succeeds).
- `/health/ready` now performs a real `$queryRaw` DB-reachability check (closed out from Phase 2's "known issue" list).
- OTP delivery is still a `console.warn`-based dev stub (`OtpService.deliver()`, clearly marked `[DEV ONLY]` in the code and docstring) — real email/SMS delivery is Phase 10's notification system. Do not treat this as production-ready; it's called out again here so it isn't missed.
- Mobile Login's "resume OTP verification for a pending-activation account" flow (docs/08) is intentionally not implemented — see the Mobile section above.
